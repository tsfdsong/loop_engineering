# 项目上下文分析 / 落地约束分析（Step ①.5 六维度）

> SKILL.md Step ①.5 的执行真源。何时读：进入 Step ①.5 时**必读**，按下列清单逐维度探测并产出。
> ⚠️ 本步分析「仓库能落地什么」——**不是** brainstorming 产品「需求分析」。
> ⚠️ 硬规则：全部 6 个维度产出完整才能准入 Step ②；任一维度缺失 → 禁止进入 Step ②。

## 维度 1: 项目身份识别

- 扫描项目文档(自动发现,不硬编码文件名):
  - CLAUDE.md / AGENTS.md / README.md / CONTRIBUTING.md
  - docs/ 下所有 .md 文件(设计文档/调研报告/方案)
  - deploy/ 下 docker-compose.yml(如有,部署架构)
- 从中提取: 项目是什么、做什么、怎么部署
- 产出: 项目类型(全栈Web/纯后端/CLI/库/技能仓库/单页应用/其他) + 部署方式(无/Docker/Serverless)

## 维度 2: 技术栈扫描

- 自动探测 manifest(不预设):
  - Python(pyproject.toml/setup.py/requirements*)
  - Node(package.json) · Go(go.mod) · Rust(Cargo.toml)
  - 多语言/无 manifest → 标注并降级为目录结构推断
- 识别: 主语言 + 框架 + DB/缓存/存储(如适用)
- 产出: 完整技术栈清单 + 版本约束（非 Web 项目标注"无前端/无DB"）

## 维度 3: 现有模块盘点

- 自动发现源码根(不硬编码路径):
  - 探测 src/ app/ lib/ cmd/ skills/ 等常见根
  - Web 项目: backend/app/* + frontend/src/*
  - 单仓多包/库: 顶层包目录
  - 技能仓库/纯文档: 按子目录/文档章节划分"模块"
- 识别: 已有哪些业务模块/包/技能/章节?
- 产出: 模块清单 + 模块职责描述（无源码项目 → 以文档/配置单元为"模块"）

## 维度 4: 功能匹配分析(★最关键)

- 新功能与哪个现有模块最相关?
- 是否可以扩展现有模块(优先)?
- 还是需要新建模块?
- 哪些已有接口/表/工具函数可以直接复用?
- 产出: 匹配结论 + 复用清单 + 新建清单

## 维度 5: 架构约束检查

- 从维度1-4探测结果**动态生成**检查项(不预设):
  - DB 项目: async/sync? ORM? 迁移工具?
  - Web 后端: 分层模式(router→service→model)?
  - Web 前端: 框架+UI库+TS模式?
  - 库/CLI: 包结构/入口约定/命名规范?
  - 技能仓库: SKILL.md frontmatter 规范?
  - 通用: 测试框架? lint/format 配置?
- 如某类不适用 → 标注"N/A"并说明,不视为缺失
- 产出: 架构约束清单(按实际项目类型裁剪) + 违背风险提醒

## 维度 6: 风险排查 + 方案生成

- 方案A(推荐): 基于维度4+5分析的最优路径
- 方案B: 备选路径(何时选?权衡了什么?)
- 风险评估: 改了核心链路?有数据迁移?
- 产出: 推荐方案 + 替代方案 + 风险清单

完成后自动写入 `decision_log`（按维度1探测结果填充，N/A 项明确标注）：

```

  采纳理由: [基于维度4+5的推理]

```

- 全部 6 个维度产出完整 → ✅ 准入 Step ②
