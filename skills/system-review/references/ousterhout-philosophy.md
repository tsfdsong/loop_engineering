# Ousterhout 设计哲学背靠（Step 2 按需加载）

> 来源：John Ousterhout《A Philosophy of Software Design》。本文件是 system-review Step 2 纵向架构深度审查的理论背靠；评估模块深浅、信息隐藏、复杂度累积时按需读取。原 system-review SKILL.md 附录（v6.4 迁入），v1.4 改为渐进披露按需加载。

## A.1 复杂度是渐增的

**软件复杂度不是单一决策的产物，而是无数小决策的累积。**

- 每次"为现在省事"的设计选择都会增加未来的认知负担
- 复杂度 = 依赖（模块间耦合）+ 晦涩（代码意图不清晰）+ 重复
- **战术编程 vs 战略编程**：战术编程写完能跑就完（短期快，长期难）；战略编程每次决策考虑未来 6 个月的可维护性

**system-review 应用**：Step 3 持续改进审查时，问每个改动"是战术还是战略？"——"战术编程的积累"本身就是技术债。

## A.2 深模块 vs 浅模块

**少量复杂接口（深模块）> 大量简单接口（浅模块）。**

```
浅模块（差）：
┌────────────────────┐
│ getName()          │
│ getEmail()         │
│ getAge()           │ ← 10 个简单 getter
│ getPhone()         │
│ ...                │
└────────────────────┘
接口复杂，实现简单 → 调用方累

深模块（好）：
┌────────────────────┐
│ sendInvitation()   │ ← 1 个复杂接口
└────────────────────┘
接口简单，实现可以复杂 → 调用方轻松
```

**深模块特征**：强大功能 / 简单接口；隐藏实现细节；调用方不需要理解内部。

**system-review 应用**：Step 2 抽象恰当检查——每个模块是"深"还是"浅"？浅模块是"重新发明参数"的反模式。

## A.3 信息隐藏（Information Hiding）

**模块不应暴露不必要的信息。**

| 应隐藏 | 不应暴露 |
|-------|---------|
| 内部数据结构 | 数据库 schema 细节 |
| 算法选择 | 配置格式 |
| 性能优化细节 | 内部状态 |
| 第三方库封装 | 异常实现细节 |

**system-review 应用**：Step 2 抽象恰当——模块边界是否清晰？"穿层调用"（UI 直接查 DB）= 信息隐藏失败。

## A.4 复杂度来源（4 大类）

| 来源 | 描述 | system-review 检测 |
|------|------|-------------------|
| **依赖** | 模块间不必要的耦合 | 依赖图分析、循环依赖 |
| **晦涩** | 代码意图不清晰 | 命名/注释质量 |
| **重复** | 相同逻辑多处出现 | 重复率检测 |
| **复杂性累积** | 每个小决策叠加 | 战术编程积累检测 |

## A.5 设计策略

| 策略 | 实现 |
|------|------|
| **正交性** | 模块互不依赖（改 A 不影响 B） |
| **深模块** | 用小接口封装复杂实现 |
| **信息隐藏** | 不暴露不必要的信息 |
| **分层抽象** | 每层只关注自己职责 |
| **小接口、大实现** | 减少调用方负担 |

## A.6 设计哲学与三步方法论的对应

| system-review 步骤 | Ousterhout 背靠 |
|-------------------|----------------|
| Step 1 横向自洽性 | 信息隐藏失败会引发不一致（接口穿层 → 字段不对齐） |
| Step 2 纵向架构深度 | 浅模块 / 深模块 / 正交性 / 抽象恰当 |
| Step 3 持续改进 | 战术编程 vs 战略编程 / 复杂度累积检测 |

## A.7 决策启发

1. **新增功能时**：选深模块设计，避免"快速加 5 个 getter"
2. **重构时**：问"这是把浅模块改深，还是把深模块拆浅？"
3. **审查时**：每个模块问"它的接口能更简单吗？"
4. **决策时**：用 6 个月视角判断战术 vs 战略

## A.8 不适用场景

- ❌ **过度抽象**：深模块不意味着"全部隐藏到不可见"
- ❌ **架构层次过多**：分层抽象不是"无限分"
- ❌ **回避性能**：信息隐藏不能以性能为借口
