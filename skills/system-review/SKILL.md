# System Review — 三步系统级审查方法论

从"审查项目"层面的三类常见问题出发，串联三条方法论。每步检查清单附 ATAM/arc42 业界参考检查点。

## 核心定位

| 维度 | system-review（本技能） | code-reviewer |
|------|------------------------|----------------|
| 审查对象 | 项目/模块/系统 | 单文件/单 PR |
| 关注重点 | 一致性、职责、改进 | 代码质量、安全 |
| 适用阶段 | 设计/重构/集成/重大变更 | 每次 PR |

> 两技能不互斥，是不同粒度的审查。一次大型重构可能同时用。

### 触发范围与必检项

> **仅在触发本技能时生效**（go Step ⑦.5 / 用户显式要求 / V6 架构级改动后核对）。**不**升级为 loop、单文件 PR、日常小改动的全局硬门禁。

| 项 | 规则 |
|----|------|
| **文档与实现对齐验证（§4）** | **必检** — 每份报告必含，不可跳过；无关联文档时写 `N/A` 并给 diff 依据 |
| **检查范围** | **仅本次变更相关文档** — 由 `git diff` / 变更文件列表 / 关联 spec·plan 推导，**禁止**全仓历史文档逐条扫 |

## 三步方法论总览

```
Step 1: 横向自洽性检查 ── 组件间是否一致
Step 2: 纵向架构深度审查 ── 职责是否各司其职
Step 3: 持续改进审查 ── 哪些可增强/精简/优化（含 §4 必检）
```

每步独立可用，串联使用最系统。快速模式可只跑 Step 1 + Step 3。

## Step 1: 横向自洽性检查

**核心问题**：各组件之间是否存在矛盾——接口契约对不上、字段命名不一致、假设互相冲突。

### 检查清单

| 类别 | 检查项 | 参考 |
|------|--------|------|
| **接口契约** | 模块A声称的输入/输出，与模块B实际调用的参数类型/命名是否一致？ | (ATAM: 场景 / arc42: §3) |
| **字段对齐** | 同一概念在不同层（API/DTO/DB）的字段名/类型/可选性是否一致？ | (arc42: §5) |
| **命名一致** | 核心实体的命名在所有引用点是否统一？ | (arc42: §12) |
| **配置假设** | 各模块对环境/配置/权限的假设是否互相矛盾？ | (ATAM: 质量属性) |
| **错误处理约定** | 各模块的错误码/异常类型/重试策略是否一致？ | (arc42: §6) |
| **状态机一致** | 跨模块的同一对象状态定义是否相同？ | (ATAM: 场景) |
| **数据流向** | 数据从输入到持久化的路径上，各环节对数据结构的假设是否一致？ | (arc42: §5) |
| **协议版本** | 客户端/服务端的 API 版本、序列化格式是否对齐？ | (ATAM: 性能) |

### 检查步骤

1. 列出系统核心组件（API 层、领域层、基础设施层、外部服务）
2. 对每个**跨组件边界**，过一遍上表检查项
3. 记录每个矛盾点：**预期 vs 实际** + 影响范围
3.5 **边界值探测**：对本次 diff 新引入的配置入口 / 参数 / 路径 / 分支，逐一推演边界输入（空值、纯文件名、极端值、未定义输入）——盲评测证：这是最常漏检的崩溃源（如 `os.makedirs("")`）
4. 按影响排序：阻塞型（运行时会崩）> 隐藏型（边缘场景）> 优雅降级型

检查项无发现时显式记录"未发现"（含 N/A 及理由，如"协议版本 N/A：无对外 API"），禁止静默省略——防"没查"与"查了没问题"混淆。

**输出标签**：`[CRITICAL]` / `[HIDDEN]` / `[MINOR]`

**定级前自检**：① 该发现运行时是否直接崩溃 / 产生错误行为？否 → 降 HIDDEN；② 是否与已有 CRITICAL 同根因？是 → 并档不重复计。每个发现附 `文件:行号`，行号引用后回读原文核对一次。

## Step 2: 纵向架构深度审查

**核心问题**：分层、职责、链路是否合理？每个组件是否做且只做它该做的事？

### 检查清单

| 类别 | 检查项 | 参考 |
|------|--------|------|
| **职责单一** | 每个模块/类是否只做一件事？有无"上帝类/上帝模块"？ | (ATAM: 可修改性) |
| **分层清晰** | 依赖方向是否单向？有无反向依赖？ | (arc42: §4) |
| **链路完整** | 核心用例的端到端链路能否画出来？有无断点？ | (arc42: §6) |
| **抽象恰当** | 抽象层级是否一致？有无"上帝接口"或"过度抽象"？ | (ATAM: 可修改性) |
| **设计必要性** | 新增模块/抽象/配置是否被当前需求或质量属性明确证明？有无更简单做法？ | (arc42: §4) |
| **质量属性** | 性能/可用性/安全/可修改性是否被显式处理？ | (ATAM 核心) |
| **决策可追溯** | 重要架构决策是否记录了理由（ADR）？ | (arc42: §9) |
| **风险可见** | 技术债和风险是否被记录追踪？ | (arc42: §11) |
| **部署合理** | 架构是否与部署模型一致？ | (arc42: §7) |

### 检查步骤

1. 画**组件图**（按层次而非按功能）
2. 对每个组件检查"职责单一"与"抽象恰当"
3. 对每条**跨层调用**检查依赖方向
4. 选 3-5 个**核心用例**，逐个追踪端到端链路（含异常路径，非仅 happy path）
5. 对新增抽象/模块/配置做**必要性审查**（见下）
6. 检查 ADR 与技术债记录

### 轻量必要性判断

> 只审**设计必要性**，不扩展为完整方案设计评审器；不回答"产品上该不该做"。

1. 这层抽象/模块/协议，是否被**当前需求、验收条件或质量属性**明确要求？
2. 是否存在**更简单**、同样满足目标的做法？
3. 新复杂度的收益是否足以抵消理解/调用/配置成本？

**输出标签**：`[JUSTIFIED]`（复杂度有明确收益）/ `[OVERDESIGNED]`（超出需求，有更简单方案）/ `[UNPROVEN]`（可能合理但证据不足）

典型信号：单一调用方却引入多层适配器/registry → 疑似过度设计；仅以"以后可能会用"为理由 → 默认不成立。

> **理论背靠（按需加载）**：Ousterhout《A Philosophy of Software Design》的深模块/信息隐藏/复杂度累积等核心思想，及与本三步方法论的对应关系，见 `references/ousterhout-philosophy.md`。Step 2 需要评估模块深浅、信息隐藏失败或复杂度累积时读取。

## Step 3: 持续改进审查

**核心问题**：当前系统中哪些可以增强、精简或优化？

### 检查清单

| 类别 | 检查项 | 参考 |
|------|--------|------|
| **冗余代码** | 功能重复的代码/模块？可否合并？ | (arc42: §5) |
| **文档实现对齐** | README/设计文档/配置样例中的能力、入口、约束、默认值与当前实现逐项对齐？→ **必检 §4** | (arc42: §9/§11) |
| **废弃功能** | 已标记废弃但仍在使用/导出的功能？ | (ATAM: 可修改性) |
| **可强化点** | 缺错误处理/测试/日志/验证的地方？ | (ATAM: 可用性) |
| **简化机会** | 过度设计、过度抽象、可简化的部分？ | (arc42: §4) |
| **性能瓶颈** | 明显的 N+1、重复计算、不必要的 IO？ | (ATAM: 性能) |
| **安全加固** | 输入都验证？敏感操作都审计？ | (ATAM: 安全) |
| **可观测性** | 关键路径有日志/指标/追踪？ | (arc42: §6) |

### 检查步骤

1. 从 Step 1/2 的发现出发，收集**改进候选**
2. 按投入产出比排序：高价值低投入 > 低价值高投入
3. **必做 §4 文档与实现对齐验证**（规则见下节）
4. 区分**立即做**（安全/阻塞）、**下迭代做**（性能/增强）、**技术债登记**（需追踪）
5. 写入项目级 TODO 或 issue 跟踪

**输出格式**：改进路线图按 🔴 立即做 / 🟡 下迭代做 / 🟢 技术债登记 三档列出。

## §4 文档与代码实现一致性核对（必检）

> 把"文档↔代码一致性"从泛化的"过时文档"扩展为**可执行的对齐验证**。仅触发本技能时强制，不升级为全局门禁。

### 规则

| 规则 | 说明 |
|------|------|
| **何时必检** | go Step ⑦.5、用户显式 system-review、V6 架构级改动后核对 |
| **何时不检** | 未触发本技能的 loop / 单 PR / 小改动 |
| **范围** | **仅本次变更相关文档** |
| **跳过判定** | 无关联文档 → §4 写 `N/A（本次变更无文档面）` + diff 依据，**不得**省略 §4 标题 |

### 范围推导

1. 从 `git diff` / 变更文件列表提取被改动的 `.md`、注释、配置样例、SKILL.md、README 片段
2. 从代码变更反查：改了某行为，则纳入**直接描述该行为**的文档（即使该文档不在 diff 中）
3. **禁止**为凑覆盖而扫描全仓 README、全部 docs/、历史 spec
4. 深度/季度模式：范围 = 审查声明的主题所涉文档，仍非全仓扫描

### 核查步骤与差异标签

1. 列出本次变更涉及的关键文档与代码入口；除文档说法外，核对**新增配置/环境变量的行为约束**（读取时机、生效范围、边界值行为）是否有文档说明
2. 逐项对照：文档说什么 vs 代码实际做什么
3. 标记：**[STALE]** 文档落后于实现 / **[MISSING]** 代码有行为但文档未说明 / **[DRIFT]** 两边对同一规则描述不同 / **[OK]** 一致
4. 影响理解或操作路径 → 至少 HIDDEN；导致错误操作 → CRITICAL

## 执行模式

| 模式 | 适用 | 范围 |
|------|------|------|
| **快速**（15-30 分钟） | 日常小变更后、交付前 | Step 1 接口契约+字段对齐；Step 3 立即项 ≤5 条；§4 必检 |
| **完整**（1-3 小时） | 重大重构前、新模块集成、季度审查 | 三步全清单；§4 必检 |
| **深度**（1-2 天） | 年度架构审查、并购评估 | 三步 + ATAM 质量场景 + arc42 全文档；多 session 并行 |

```markdown
[1-2 句总结 + 优先级建议]
```

## 使用场景

| 场景 | 推荐模式 | 关注重点 |
|------|---------|---------|
| 新模块接入项目 | 快速 | Step 1 接口契约 + 文档入口对齐 |
| 重大重构前 | 完整 | 全部三步 + §4 |
| 定期项目健康检查 | 完整 | Step 2 + Step 3 + 文档漂移 |
| 性能问题排查 | 快速 | Step 2 质量属性 + Step 3 性能 |
| 安全审计 | 完整 | Step 1 + Step 2 + ATAM 安全参考 |
| 团队入职项目了解 | 完整 | 用审查过程倒推系统全貌 |

## 与其他技能配合

- `code-reviewer` — 单 PR/单文件代码层审查；system-review 发现代码异味时可看是否反映系统层设计问题
- `brainstorming` — 发现问题后探索解决方案
- `spec-driven-development` — 改进路线图确定后写实施计划
- `subagent-driven-development` — 深度模式拆分多 session 并行审查
- `systematic-debugging` — 紧急 hotfix 场景（本技能不适用于紧急修复）

## 局限

- **不替代代码级审查** — 代码异味、bug、安全漏洞走 code-reviewer
- **不替代实际测试** — 路线图中"补全测试"需 testing 配合
- **不替代人工判断** — 输出是 AI 分析，最终决策需用户确认
- **不适用于紧急 hotfix** — 走 systematic-debugging
- **§4 非全局门禁** — 仅触发本技能时强制

## V6 一致性核对协同（触发后操作手册）

> AGENTS.md V6 一句话铁律的落地细节：何时查、维度怎么选、查完怎么办。检查方法本身走上面三步方法论，不在此重复。

### 维度规则

| 规则 | 说明 |
|------|------|
| **维度 4（文档↔代码）** | **强制必检**，不问用户、不可跳过；范围 = 本次变更相关文档 only（见 §4） |
| **维度 1–3** | 用 `AskUserQuestion`（multiSelect）让用户选**额外**覆盖，**至少再选 1 个**（推荐全选） |
| **禁止** | 因用户未勾选维度 4 而跳过 §4；把"至少选 1 维"理解成可跳过文档对齐 |

Ask 选项示例：`(推荐)` 完整（1+2+3，外加已强制的 4）· 轻量（1+3）· 单维。

### 维度映射

| V6 维度 | 检查方法 |
|---------|---------|
| 1 需求↔实现 | 本技能三步不覆盖，由 V6 红线自含：计划/PRD vs 已实现代码，标 [GAP]/[EXTRA] |
| 2 模块间横向一致性 | **Step 1 检查清单** |
| 3 端到端链路打通 | **Step 2 链路完整**检查项 |
| 4 文档↔代码 | **§4 必检** |

### 处置协议

非交互/报告型运行（subagent、离线审查）无法弹 AskUserQuestion 时：处置建议以附表呈现并逐行标注"待用户确认"；回到交互会话后必须转 AskUserQuestion 补决策。

发现不一致 → **不得**自行决定修复/忽略，必须为每个差异项（或合理分组）调 AskUserQuestion：

| 选项 | 含义 | 推荐场景 |
|------|------|---------|
| **立即修复** | 阻断下个任务，先修 | CRITICAL / 阻塞型（默认 `(推荐)`） |
| **登记后续修复** | 记 TODO，继续下个任务 | HIDDEN / 非阻塞型 |
| **标记已知边界** | 不修但文档说明 | 设计取舍 |
| **忽略** | 不修不记录 | 误报 |

> 处置本身是决策点，必须走 AskUserQuestion（红线 C2），禁止文字列选项。
