# Context-Driven Development（上下文驱动开发）

把项目上下文作为与代码并肩管理的受管工件来实施和维护，通过结构化的项目文档实现一致的 AI 交互与团队对齐。

## 何时使用

- 用 Conductor 搭建新项目
- 理解上下文工件之间的关系
- 跨 AI 辅助开发会话保持一致性
- 帮新成员 onboard 到既有 Conductor 项目
- 决定何时更新上下文文档
- 管理 greenfield 与 brownfield 项目上下文

## 核心理念

Context-Driven Development 把项目上下文当作与代码并肩管理的一等工件。不依赖临时 prompt 或散落的文档，而是建立一个持久的、结构化的基础来支撑所有 AI 交互。

关键原则：

1. **上下文先于代码**：实现之前先定义在做什么、怎么做
2. **活文档**：上下文工件随项目演进
3. **单一真源**：每类信息只有一个权威位置
4. **AI 对齐**：一致的上下文产生一致的 AI 行为

## 工作流

遵循 **Context → Spec & Plan → Implement** 工作流：

1. **Context 阶段**：建立或验证项目上下文工件存在且最新
2. **Specification 阶段**：为工作单元定义需求与验收标准
3. **Planning 阶段**：把 spec 拆为分阶段的可执行任务
4. **Implementation 阶段**：按既定工作流模式执行任务

## 工件关系

### product.md —— 定义 WHAT 与 WHY

用途：承载产品愿景、目标、目标用户与业务背景。

内容：

- 产品名与一句话描述
- 问题陈述与解法方向
- 目标用户画像
- 核心功能与能力
- 成功指标与 KPI
- 产品路线图（高层）

何时更新：

- 产品愿景或目标变化
- 规划新的重要功能
- 目标人群转移
- 业务优先级演进

### product-guidelines.md —— 定义如何沟通

用途：确立品牌语调、消息标准与沟通模式。

内容：

- 品牌语调与风格指南
- 术语表
- 报错文案规范
- 面向用户的文案标准
- 文档风格

何时更新：

- 品牌指南变化
- 引入新术语
- 沟通模式需要调整

### tech-stack.md —— 定义用什么

用途：记录技术选型、依赖与架构决策。

内容：

- 主语言与框架
- 关键依赖及版本
- 基础设施与部署目标
- 开发工具与环境
- 测试框架
- 代码质量工具

何时更新：

- 新增依赖
- 升级大版本
- 基础设施变化
- 采用新工具或新模式

### workflow.md —— 定义怎么干活

用途：确立开发实践、质量闸门与团队工作流。

内容：

- 开发方法论（TDD 等）
- Git 工作流与 commit 规范
- 代码评审要求
- 测试要求与覆盖率目标
- 质量保证闸门
- 部署流程

何时更新：

- 团队实践演进
- 质量标准变化
- 采用新工作流模式

### tracks.md —— 记录正在发生什么

用途：全部工作单元的注册表，含状态与元数据。

内容：

- 进行中 track 及当前状态
- 已完成 track 及完成日期
- track 元数据（类型、优先级、负责人）
- 各 track 目录链接

何时更新：

- 新建 track
- track 状态变化
- track 完成或归档

## 上下文维护原则

### 保持工件同步

一个工件的变化要反映到相关文档：

- product.md 新增功能 → 若需新依赖则更新 tech-stack.md
- track 完成 → 更新 product.md 反映新能力
- workflow 变化 → 更新所有受影响的 track 计划

### 加依赖时更新 tech-stack.md

新增任何依赖之前：

1. 检查既有依赖能否满足需求
2. 记录新依赖的理由
3. 加版本约束
4. 注明配置要求

### 功能完成时更新 product.md

完成一个功能 track 后：

1. 在 product.md 中把功能从"planned"移到"implemented"
2. 更新受影响的成功指标
3. 记录与原计划的范围偏差

### 实现前验证上下文

开始任何 track 之前：

1. 读全部上下文工件
2. 标记过时信息
3. 先提出更新再继续
4. 与相关人确认上下文准确

## Greenfield 与 Brownfield 处理

### Greenfield 项目（新建）

新项目：

1. 运行 `/conductor:setup` 交互式创建全部工件
2. 回答产品愿景、技术偏好、工作流问题
3. 为选定语言生成初始风格指南
4. 创建空的 tracks 注册表

特征：

- 完全掌控上下文结构
- 代码存在之前先定标准
- 尽早确立模式

### Brownfield 项目（既有）

既有代码库：

1. 运行 `/conductor:setup`（带既有代码库探测）
2. 系统分析既有代码、配置与文档
3. 基于发现的模式预填工件
4. 评审并精化生成的上下文

特征：

- 从既有代码提取隐性上下文
- 调和既有模式与期望模式
- 记录技术债与现代化计划
- 既确立标准又保留可用模式

## 收益

### 团队对齐

- 新成员凭显式上下文更快 onboard
- 全团队术语与约定一致
- 对产品目标与技术决策有共同理解

### AI 一致性

- AI 助手跨会话产出对齐的结果
- 减少每次交互重复解释上下文
- 基于文档化标准的可预期行为

### 组织记忆

- 决策与理由被保留
- 上下文在人员变动中存续
- 历史上下文为未来决策提供参考

### 质量保证

- 标准显式且可验证
- 偏离上下文可被检测
- 质量闸门有文档且可执行

## 上下文生命周期

1. **创建**：经 `/conductor:setup` 初始建立
2. **验证**：每个 track 前验证
3. **演进**：随项目成长更新
4. **同步**：保持工件对齐
5. **归档**：记录历史决策

## 上下文验证清单

在任何 track 上开始实现之前，验证上下文：

### 产品上下文

- [ ] product.md 反映当前产品愿景
- [ ] 目标用户描述准确
- [ ] 功能列表最新
- [ ] 成功指标已定义

### 技术上下文

- [ ] tech-stack.md 列出全部当前依赖
- [ ] 版本号准确
- [ ] 基础设施目标正确
- [ ] 开发工具已记录

### 工作流上下文

- [ ] workflow.md 描述当前实践
- [ ] 质量闸门已定义
- [ ] 覆盖率目标已明确
- [ ] commit 规范已记录

### Track 上下文

- [ ] tracks.md 显示全部进行中的工作
- [ ] 无过期或废弃 track
- [ ] track 间依赖已标注

## 常见反模式

避免这些上下文管理错误：

### 过期上下文

问题：上下文文档过时且有误导性。
解法：把更新上下文纳入每个 track 的完成流程。

### 上下文蔓延

问题：信息散落多处。
解法：用定义好的工件结构；克制创建新文档类型。

### 隐性上下文

问题：依赖未写入工件的知识。
解法：反复引用的东西就加进对应工件。

### 上下文囤积

问题：一个人维护上下文，无团队输入。
解法：在 PR 中评审上下文工件；更新协作化。

### 过度规格化

问题：上下文细到无法维护。
解法：工件聚焦于影响 AI 行为与团队对齐的决策。

## 与开发工具集成

### IDE 集成

配置 IDE 突出显示上下文文件：

- 固定 conductor/product.md 便于速查
- 把 tech-stack.md 加进项目备注
- 从风格指南为常见模式建 snippet

### Git Hooks

考虑 pre-commit hook：

- 依赖变化但 tech-stack.md 未更新时告警
- 功能分支 merge 时提醒更新 product.md
- 校验上下文工件语法

### CI/CD 集成

流水线中加入上下文验证：

- 检查 tech-stack.md 与实际依赖一致
- 验证上下文文档内链接可解析
- 确保 tracks.md 状态与 git 分支状态一致

## 会话连续性

Conductor 通过上下文持久化支持多会话开发：

### 开始新会话

1. 读 index.md 定位
2. 查 tracks.md 看进行中工作
3. 看相关 track 的 plan.md 确定当前任务
4. 验证上下文工件最新

### 结束会话

1. 用当前进度更新 plan.md
2. 记录阻塞点与已做决策
3. 带清晰状态 commit 进行中的工作
4. 状态变化则更新 tracks.md

### 处理中断

任务中被打断时：

1. 把任务标记为 `[~]` 并注明停止点
2. 把进行中的工作 commit 到功能分支
3. 在 plan.md 中记录未 commit 的决策

## 最佳实践

1. **先读上下文**：开工前永远先读相关工件
2. **小步更新**：增量改上下文，不大规模重写
3. **关联决策**：实现选型时引用上下文
4. **上下文随代码入库**：上下文改动与代码改动一起 commit
5. **评审上下文**：代码评审中包含上下文工件评审
6. **定期验证**：大工作前跑上下文验证清单
7. **同步变更**：上下文工件显著变化时通知团队
8. **保留历史**：用 git 跟踪上下文演进
9. **质疑过期**：上下文感觉不对就调查并更新
10. **保持可操作性**：每条上下文都应能指导一个决策或行为

## 边界

- 仅当任务明确匹配上述范围时使用本技能。
- 不要把输出当作环境特定验证、测试或专家评审的替代品。
- 缺少必需输入、权限、安全边界或成功标准时，停下来问清楚。
