# Systematic Debugging（系统化调试）

## 概述

随机修复浪费时间还制造新 bug。快补丁掩盖底层问题。

**核心原则：** 尝试修复之前**永远**先找到根因。症状级修复就是失败。

**违反此流程的字面即违反调试的精神。**

## The Iron Law

```
NO FIXES WITHOUT ROOT CAUSE INVESTIGATION FIRST
```

没完成 Phase 1，就不能提修复方案。

## 何时使用

用于**任何**技术问题：
- 测试失败
- 生产 bug
- 异常行为
- 性能问题
- 构建失败
- 集成问题

**以下情况尤其要用：**
- 时间压力下（紧急让瞎猜变得诱人）
- "就一个快修"看起来很明显
- 已经试过多个修复
- 上一个修复没生效
- 你没有完全理解问题

**以下情况不要跳过：**
- 问题看起来简单（简单 bug 也有根因）
- 你在赶时间（赶时间保证返工）
- 经理要求"现在就修好"（系统化比瞎扑腾快）

## 四个阶段

必须完成每个阶段再进下一个。

### Phase 1: 根因调查

**尝试任何修复之前：**

1. **仔细读报错信息**
   - 不要跳过 error 或 warning
   - 它们常常包含确切答案
   - 完整读 stack trace
   - 记下行号、文件路径、错误码

2. **稳定复现**
   - 能可靠触发吗？
   - 确切步骤是什么？
   - 每次都发生吗？
   - 不可复现 → 收集更多数据，不要猜

3. **检查最近改动**
   - 什么变了可能引起这个问题？
   - git diff、最近 commit
   - 新依赖、配置变更
   - 环境差异

4. **多组件系统中收集证据**

   **当**系统有多个组件（CI → build → 签名，API → service → 数据库）时：

   **提出修复前，先加诊断埋点：**
   ```
   For EACH component boundary:
     - Log what data enters component
     - Log what data exits component
     - Verify environment/config propagation
     - Check state at each layer

   Run once to gather evidence showing WHERE it breaks
   THEN analyze evidence to identify failing component
   THEN investigate that specific component
   ```

   **示例（多层系统）：**
   ```bash
   # Layer 1: Workflow
   echo "=== Secrets available in workflow: ==="
   echo "IDENTITY: ${IDENTITY:+SET}${IDENTITY:-UNSET}"

   # Layer 2: Build script
   echo "=== Env vars in build script: ==="
   env | grep IDENTITY || echo "IDENTITY not in environment"

   # Layer 3: Signing script
   echo "=== Keychain state: ==="
   security list-keychains
   security find-identity -v

   # Layer 4: Actual signing
   codesign --sign "$IDENTITY" --verbose=4 "$APP"
   ```

   **这能揭示：** 哪一层失败（secrets → workflow ✓，workflow → build ✗）

5. **追踪数据流**

   **当**错误深埋在调用栈中时：

   完整的回溯技术见本目录 `root-cause-tracing.md`。

   **速查版：**
   - 坏值从哪来？
   - 谁用坏值调了这里？
   - 一路向上追到源头
   - 在源头修，不在症状修

### Phase 2: 模式分析

**修复前先找模式：**

1. **找可用的同类示例**
   - 在同一代码库找类似的正常工作的代码
   - 与坏掉的类似的、正常的东西是什么？

2. **对照参考实现**
   - 实现某个模式时，**完整**读参考实现
   - 不许略读——逐行读
   - 完全理解模式再应用

3. **识别差异**
   - 正常的与坏掉的之间差在哪？
   - 列出每一个差异，再小也要列
   - 不要假设"这个不可能有影响"

4. **理解依赖**
   - 它还需要哪些组件？
   - 什么设置、配置、环境？
   - 它做了哪些假设？

### Phase 3: 假设与验证

**科学方法：**

1. **提出单一假设**
   - 清楚陈述："我认为 X 是根因，因为 Y"
   - 写下来
   - 要具体，不要含糊

2. **最小化测试**
   - 做出**最小**改动来验证假设
   - 一次一个变量
   - 不许同时修多处

3. **继续前先验证**
   - 生效了？→ Phase 4
   - 没生效？→ 提**新**假设
   - **不许**在旧修复上叠新修复

4. **不懂的时候**
   - 说"我不理解 X"
   - 不许装懂
   - 求助
   - 再研究

### Phase 4: 实施

**修根因，不修症状：**

1. **建失败测试用例**
   - 最简单的可复现
   - 可能的话写成自动化测试
   - 无框架就写一次性脚本
   - 修复前**必须**有
   - 用 `superpowers:test-driven-development` 技能写规范的失败测试

2. **实施单一修复**
   - 针对已定位的根因
   - 一次一处改动
   - 不许"顺手改进"
   - 不许捆绑重构

3. **验证修复**
   - 测试现在过了吗？
   - 没弄坏其他测试吗？
   - 问题真的解决了吗？

4. **修复不生效时**
   - 停
   - 数一数：已经试了几次修复？
   - < 3 次：回 Phase 1，带着新信息重新分析
   - **≥ 3 次：停下，质疑架构（见下方第 5 步）**
   - **不许**不做架构讨论就尝试第 4 次修复

5. **3+ 次修复失败时：质疑架构**

   **架构问题的信号：**
   - 每次修复都暴露新地方的新共享状态/耦合/问题
   - 修复需要"大重构"才能落地
   - 每次修复都在别处制造新症状

   **停下，质疑根本：**
   - 这个模式本质上站得住吗？
   - 我们是不是"纯靠惯性硬撑"？
   - 该重构架构，还是继续修症状？

   **与 human partner 讨论后再尝试更多修复。**

   这不是"假设失败"——这是架构错了。

## Red Flags —— 停下，回流程

发现自己在想这些：
- "先快修，回头再查"
- "改下 X 试试看能不能好"
- "多改几处一起跑测试"
- "跳过测试，我手动验证"
- "大概是 X，直接修它"
- "我没完全懂但这个可能行"
- "模式说 X 但我换个方式适配"
- "主要问题是这些："[没调查就列修复]
- 数据流还没追就提方案
- **"再试一次修复"（已试过 2+ 次）**
- **每次修复都暴露不同位置的新问题**

**以上任何一条 = 停下，回 Phase 1。**

**3+ 次修复失败：** 质疑架构（见 Phase 4.5）。

## human partner 的纠偏信号

**注意这些redirect：**
- "Is that not happening?" —— 你没验证就假设了
- "Will it show us...?" —— 你早该加证据收集
- "Stop guessing" —— 你没理解就提修复
- "Ultrathink this" —— 质疑根本，不只症状
- "We're stuck?"（沮丧）—— 你的路子不对

**看到这些：** 停下，回 Phase 1。

## 常见合理化借口

| 借口 | 现实 |
|------|------|
| "问题很简单，不需要流程" | 简单问题也有根因。流程对简单 bug 很快。 |
| "紧急，没时间走流程" | 系统化调试比瞎猜乱试**更快**。 |
| "先试这个，再调查" | 第一次修复定调子。从一开始就做对。 |
| "修好确认后我再补测试" | 没测试的修复站不住。先测试才能证明。 |
| "一次修多处省时间" | 无法隔离哪处生效。还会引入新 bug。 |
| "参考太长，我适配下模式" | 半懂保证出 bug。完整读它。 |
| "我看到问题了，直接修" | 看到症状 ≠ 理解根因。 |
| "再试一次"（已失败 2+ 次） | 3+ 次失败 = 架构问题。质疑模式，别再修。 |

## Quick Reference

| 阶段 | 关键活动 | 成功标准 |
|-------|---------------|------------------|
| **1. 根因** | 读报错、复现、查改动、收证据 | 理解 what 和 why |
| **2. 模式** | 找正常示例、对照 | 识别差异 |
| **3. 假设** | 成型理论、最小验证 | 确认或换新假设 |
| **4. 实施** | 建测试、修复、验证 | bug 解决、测试通过 |

## 流程揭示"无根因"时

若系统调查揭示问题确属环境、时序或外部因素：

1. 流程已完成
2. 记录调查了什么
3. 实施恰当处理（重试、超时、报错文案）
4. 为将来调查加监控/日志

**但是：** 95% 的"无根因"其实是调查不彻底。

## 支撑技术

以下技术属于系统化调试的一部分，在本目录中：

- **`root-cause-tracing.md`** —— 沿调用栈回溯 bug 找到最初触发点
- **`defense-in-depth.md`** —— 找到根因后在多层加校验
- **`condition-based-waiting.md`** —— 用条件轮询替换任意超时

**相关技能：**
- **superpowers:test-driven-development** —— 建失败测试用例（Phase 4 第 1 步）
- **superpowers:verification-before-completion** —— 宣称成功前验证修复生效

## 真实成效

来自调试会话的数据：
- 系统化方法：15-30 分钟修复
- 随机修复：2-3 小时瞎扑腾
- 一次修复成功率：95% vs 40%
- 引入新 bug：接近零 vs 常见

## 论源（v1.0.5 工程实践红线对接）

本技能作为以下工程实践红线的**方法论支撑**（单点真源引用，AGENTS.md §9）：

- **R3.1 根因分析** — 直接对应本技能 Iron Law「NO FIXES WITHOUT ROOT CAUSE INVESTIGATION FIRST」；禁止症状级修复（吞异常 / 改判断绕过 / 加默认值掩盖）
- **R3.5 同根 Bug 扫描红线** — 对应本技能 Phase 3（Root Cause）的"变体识别"扩展；要求根因定位到机制层后，全仓搜索同机制所有调用点，列出全部受影响位置后一次性修复全部或登记 deferred

> **红线触发场景**：任何 AI 修复 Bug / 排查故障 / 处理测试失败时，必须遵循 R3.1 + R3.5；本技能提供根因分析 5 阶段方法论（Reproduce → Isolate → Root Cause → Fix → Verify）+ 同根变体扫描 4 步流程（定位机制 → 全仓搜索 → 列位置 → 全修 / defer）。
